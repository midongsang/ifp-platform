# IFP 业务侧培训材料（产品 / 业务分析师）

> 受众：业务、产品分析师，不需要懂 SMT、AST 这些底层技术。
> 重点：怎么用 IFP 解决日常的业务规则痛点、建模怎么做、交付物是什么、怎么参与评审。
> 时长建议：60 分钟。配套：[核心概念](#6-ifp-核心概念业务易懂版) · [退款域示例](../examples/refund/refund.ifp) · [DSL 语法规范](dsl-spec.md)

---

## 1. 我们现在遇到的业务规则痛点

- 需求文档写了一大段文字，产品、开发、测试对同一条规则的理解不一样，上线就出问题。
- 边界场景、多条件叠加的场景很难想全，很多漏洞要到上线后才暴露。
- 规则改了之后不知道会影响哪些旧逻辑，变更风险只能靠人工经验判断。
- 审计来了要到处找规则依据和变更记录，整理材料很费时间。
- 历史资损复盘下来，根源多半是规则文字有歧义，或者漏掉了组合边界场景。

自然语言适合沟通，但不适合当高风险资金规则的唯一基准，问题就出在这里。

---

## 2. 为什么要形式化业务规则

把业务规则写成结构化、机器可校验的模型，换来的是几件事：

1. **消歧义**：产品、业务、开发、审计用同一套规则定义。
2. **风险前置**：编码之前就让求解引擎去找规则冲突和边界漏洞，少一些上线后的资损。
3. **变更可控**：用语义 Diff 看清"业务规则层面"到底改了什么；核心基线规则改动必须审批。
4. **审计降本**：变更和验证过程自动留痕，少花人工取证的功夫。
5. **测试提效**：自动补出人工容易漏掉的边界场景。

---

## 3. IFP 是什么（业务视角）

IFP 是意图形式化平台（Intention Formal Platform）的缩写。

它不是代码，也不是线上规则引擎，而是业务规则的一份精确说明书：写成机器读得懂的形式，
于是机器可以替你检查里面有没有矛盾、有没有漏洞。

和 Word 需求文档比一下：

| | Word 需求文档 | IFP 模型 |
| --- | --- | --- |
| 表达形式 | 自然语言 | 结构化业务描述 |
| 人能看懂 | 可以 | 可以 |
| 机器能自动校验规则冲突 / 边界场景 | 不能 | 可以 |
| 能否作为规则可信基准 | 容易过期、容易有歧义 | 可校验、可审计 |

它主要做三件事：把业务意图写清楚当需求基准、让机器去找规则冲突与超额资金这类漏洞、
记录规则变更历史并自动留存审计证据。它不写业务代码，不替代开发写逻辑，也不直接上线执行业务。

---

## 4. IFP 能做什么 / 不能做什么

**能做**

1. 统一业务规则、消除文字歧义，作为需求基线；
2. 定义业务实体、状态流转以及资金 / 数量约束（不变量）；
3. 自动搜索边界场景，找出人工想不到的漏洞；
4. 对比两次规则变更，看业务逻辑到底改了什么（语义 Diff）；
5. 给核心规则设基线，改动需要审批，全程留痕；
6. 仿真业务场景，预演多步操作会不会违规；
7. 自动输出审计日志，降低取证成本。

**不能做**

1. 不能替代开发写业务代码，也不会直接上线跑交易；
2. 发现不了纯代码 bug（比如数据库操作、网络异常）；
3. 简单 CRUD 业务投入产出比低，不强制建模；
4. 不替业务同学思考业务逻辑，只是辅助校验。

## 5. 建模交付流程（业务同学参与环节标粗）

1. 业务需求梳理【**业务/产品主导**】：梳理业务对象、状态流转、硬性约束、操作动作。
2. 编写 IFP 模型【产品 + 业务分析师 + 建模师协作】：把自然语言翻译成结构化模型。
3. 模型静态检查（自动）：平台做类型检查 + Lint，校验语法与基础规范。
4. 仿真场景验证【**业务评审**】：人工场景跑一遍，确认行为和业务预期一致。
5. 属性测试自动找漏洞（自动）：机器遍历状态组合输出反例，由业务判断反例是不是真实漏洞。
6. 模型评审【**业务必须参与评审**】：评审不变量、状态机、业务约束是否符合真实业务意图。
7. 提交、基线审批（如果涉及基线规则）。
8. 合并入库、接入 CI，后续开发以模型作为需求基准。
9. 模型版本留存，审计日志自动记录变更。

需要强调的是：模型评审是业务同学最重要的职责，要确认模型忠实还原了业务规则。

## 6. IFP 核心概念（业务易懂版）

- **限界上下文（BoundedContext）**：业务大模块，比如退款域、结算域，用来划分业务边界。
- **意图 Intent（聚合根）**：业务核心对象，例如退款单、订单；描述它的状态和约束。
- **值对象（ValueObject）**：附属信息，没有独立生命周期，比如金额、地址。
- **状态机（StateMachine）**：对象能有哪些状态、状态之间允许怎么流转（退款单：待审核 → 审核通过 → 退款完成）。
- **不变量（Invariant，最重要）**：永远不能打破的硬性业务约束。比如"退款总金额不能超过订单实付总额"，只要这条不变量在，机器就会去找有没有场景会打破它。
- **前置条件 Pre**：执行某个操作前必须满足的条件，不满足就不能操作。
- **后置条件 Post**：操作执行完成后必须保证的结果。
- **仿真场景 Scenario**：人工写的业务流程用例，用来验证模型行为。
- **属性测试 Property Test**：机器自动组合各种条件，去找违反不变量的反例。
- **基线 Baseline**：高风险的核心不变量，改动必须单独审批。
- **语义 Diff**：对比模型变更，看业务规则层面改了什么，不是单纯看文字差异。

业务同学的核心工作是梳理清楚实体、状态、不变量、前置后置条件。更完整的术语解释见[术语表中英对照](glossary.md)。

## 7. 怎么读一个 `.ifp` 模型

`.ifp` 文件用接近自然语言的结构把业务规则写下来。以退款域为例，可以当成一份分层的说明书来读：

```text
context RefundContext {              // ← 业务大模块：退款域
    description: "电商退款限界上下文……"

    intent RefundOrder {             // ← 业务核心对象：退款聚合
        field orderPaidAmount: Decimal        // 订单实付金额
        field totalRefundedAmount: Decimal = 0 // 累计已退款金额，默认 0
        field status: RefundStatus = RefundStatus::Pending // 当前状态：待审核

        state RefundStatus {         // ← 状态机：退款单有哪些状态
            Pending, Approved, Refunded, Rejected
        }
        initial: RefundStatus::Pending   // ← 初始状态：待审核

        invariant totalRefundNotExceedPaid {  // ← 不变量：硬约束
            expr: totalRefundedAmount <= orderPaidAmount
            baseline: true                    // 标为基线：修改须审批
            risk: "累计退款超过订单实付金额，造成超额退款资金损失"
            owner: "finance-team"
        }

        action ExecuteRefund(amount: Decimal) {   // ← 业务动作：执行退款
            transition: RefundStatus::Refunded
            pre: status == RefundStatus::Approved && amount >= 0  // 前置条件
            post: status == RefundStatus::Refunded                // 后置条件
                  && totalRefundedAmount == old(totalRefundedAmount) + amount
        }
    }
}
```

业务同学读模型，关注四件事就够了：

1. **实体与字段**：这个对象有哪些业务信息？
2. **状态机**：有哪些状态、允许怎么流转？
3. **不变量**：有哪些永远不能打破的硬约束？（重点）
4. **动作的 Pre/Post**：每个操作执行前要满足什么、执行后保证什么？

逗号、括号、表达式写法这些语法细节交给建模师和平台静态检查就好（详见 [DSL 语法规范](dsl-spec.md)）。

## 8. 案例：退款域建模全过程（业务视角）

背景：订单支持多次部分退款，历史上因为"多次部分退款叠加"出现过超额退款资损。

业务约束有三条：

1. 订单累计退款金额 ≤ 订单实付金额（核心不变量，设为基线）。
2. 只有"待审核"状态的退款单，才能发起审核操作。
3. 审核通过后，才能执行资金退款动作。

建模产出：

| 产出 | 内容 |
| --- | --- |
| Intent | 退款聚合（订单 + 多笔退款单）`RefundOrder` |
| 状态机 | 退款单状态流转 `Pending → Approved → Refunded`（非法流转被拦截） |
| 不变量 | 累计退款总额 ≤ 订单实付金额（基线） |
| Pre | 审核操作前置条件：退款单状态 = 待审核 |
| Scenario | 部分退款 1 次、边界全额退款、非法操作拦截场景 |

平台跑属性测试的结果，这正是历史上真实发生过的资损场景：

```text
反例 ExecuteRefund（2 步）
    不变量 totalRefundNotExceedPaid [BASELINE] 可被多步操作序列打破：
        步骤 1: Audit()
            动作前状态: orderPaidAmount=1, totalRefundedAmount=0, status=Pending
            动作后状态: orderPaidAmount=1, totalRefundedAmount=0, status=Approved
        步骤 2: ExecuteRefund(amount=2)
            动作前状态: orderPaidAmount=1, totalRefundedAmount=0, status=Approved
            动作后状态: orderPaidAmount=1, totalRefundedAmount=2, status=Refunded
        => 第 2 步执行后不变量 totalRefundNotExceedPaid 不成立
```

业务识别出这是漏洞，在需求阶段就修掉，不用等到上线踩坑。

## 9. 怎么用命令行跑一遍（`ifp check` / `verify` / `simulate`）

安装后（见 [README 快速开始](../README.md#快速开始)），在仓库根目录执行：

```bash
# ① 类型检查 + Lint：语法与建模规范是否合法
ifp check examples/refund/

# ② 属性测试：自动搜索违反不变量的反例
ifp verify examples/refund/refund.ifp

# ③ 场景仿真：按人工写的业务用例跑一遍
ifp simulate examples/refund/
```

结果怎么看：

| 命令 | 输出含义 | 业务同学关心什么 |
| --- | --- | --- |
| `ifp check` | 逐条列出 `error` / `warning`（附诊断码，如 `IFP2001`）并汇总数量 | 有没有规则缺负责人、缺风险描述等规范问题 |
| `ifp verify` | 打印发现的**反例**（动作前状态 → 执行动作 → 动作后状态，多步时为完整路径） | **反例是不是真实业务漏洞**：是则改需求/模型 |
| `ifp simulate` | 逐场景输出 `[PASS]` / `[FAIL]` 及失败原因 | 业务正向/边界/非法拦截的预期是否与模型一致 |

补充命令：

- `ifp simulate examples/refund/ --name PartialRefundOnce`：只跑指定场景。
- `ifp verify examples/refund/refund.ifp --intent RefundOrder`：只验证指定 Intent。
- `ifp baseline examples/refund/refund.ifp`：列出所有基线不变量（谁负责、风险是什么）。

退款域示例的 `ifp verify` 会按预期发现反例并以非零码退出——这正是平台的价值所在，它在编码前
就把漏洞找出来了；`ifp check` 与 `ifp simulate` 应当全部通过。

## 10. 怎么参与模型评审

模型评审清单（业务同学版），只重点检查下面几项，不用看底层表达式语法：

1. 业务实体、对象定义是否和真实业务一致？
2. 状态集合、状态流转规则是否正确？有没有遗漏允许/禁止的流转？
3. **不变量是否完整，有没有漏掉核心资金/合规约束？**（最重要）
4. 每个操作的前置条件、后置条件是否符合业务要求？
5. 仿真场景是否覆盖正向、常规异常、非法操作拦截？
6. 基线标记是否正确：高风险资金约束有没有标记基线？
7. 规则有没有和其他业务域产生冲突？跨域契约是否对齐？

不用纠结 DSL 语法对错，语法问题由建模人员和平台静态检查处理。业务评审只回答一个问题：
模型描述的业务意图，是不是真实业务规则。

（评审流程细节见[建模规范 · 模型评审流程](modeling-standard.md#12-模型评审流程)。）

## 11. 常见误区 & 避坑清单

| 误区 | 纠正 |
| --- | --- |
| IFP 模型写完就不用写需求文档 | IFP 模型是**规则可信基准**，需求文档依然保留，二者互补 |
| 所有业务规则都必须建模 | 只优先**资金、合规等高风险域**；简单低风险业务不建议建模 |
| 建模是开发的事情，业务只需提需求 | 不变量、业务约束只能由业务/产品输出，业务是规则真实性的最终责任人 |
| 只要模型过了校验，线上就绝不会出问题 | IFP 只保障**业务规则意图层面**没有漏洞；代码 bug、基础设施故障不在覆盖范围 |
| 不变量写得越多越好 | 只写硬性、永远不能打破的约束；可豁免特例走"规则豁免"审批，不写成不变量 |

## 12. 培训小结

1. IFP 本质：业务规则的精确、机器可校验模型，用来前置发现资损、合规漏洞。
2. 业务同学核心产出：业务对象、状态、不变量、前置后置约束。
3. 业务核心职责：梳理规则 + 参与模型评审，确认模型符合业务意图。
4. 落地策略：优先高风险资金域试点，从小案例起步，不要一次性全量铺开。
5. 价值：消除歧义、边界漏洞前置发现、变更风险可控、审计成本下降。

ROI 量化方式见 [ROI 测算模板](roi-template.md)；能力展望见[路线图](roadmap.md)。
